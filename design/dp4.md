# DP-4 세부 설계: 기능 레코드의 원본 파일과 변환

> **상태: 제안(미채택)**
> 이 문서는 `DESIGN.md`의 DP-4에서 결정한 내용을 기능 레코드에 대하여 구체화하는 제안이다. 사용자가 채택한 항목은 `DESIGN.md`의 DP-4에 반영하고, 이 문서에서는 제안 표시를 지운다.

## 범위

이 문서는 기능 레코드의 원본 파일(`features.yaml`)의 형식과, 원본에서 SQLite 데이터베이스를 만드는 변환을 다룬다. 항목의 이름과 테이블 정의는 [dp1.md](dp1.md)에, 변환이 실행되는 시점은 [dp5.md](dp5.md)에, 조회 스크립트는 [dp6.md](dp6.md)에 있다.

## 1. 원본 파일

기능 레코드의 원본은 데이터 폴더의 `features.yaml` 하나다. 파일은 레코드의 목록 하나로 구성한다. 트리로 중첩하지 않고 평면 목록으로 적으며(DP-1), 계층은 `parent_id`와 `path`로 나타낸다.

```yaml
# 예시
- id: NS
  name: Namespace Management
  path: Namespace Management
  parent_id: null
  description: >-
    호스트가 namespace를 생성하고 삭제하는 기능의 묶음이다.
  ims_ref: IMS-EX-0100

- id: NS-CREATE
  name: Namespace Create
  path: Namespace Management > Namespace Create
  parent_id: NS
  description: >-
    Namespace Management 커맨드(Create)로 미할당 용량에서 새 namespace를
    만들고 NSID를 할당한다. 용량이 부족하거나 namespace 수가 최대에
    도달하면 오류로 완료한다.
  ims_ref: IMS-EX-0101
```

- `path`는 최상위 항목부터 자신까지의 `name`을 ` > `로 이은 문자열이다. `parent_id`에서 계산할 수 있는 값이지만, 에이전트가 YAML 파일을 그대로 읽으므로(DP-5) 원본에 적는다. 두 값이 어긋나면 변환 단계에서 오류로 처리한다.
- 최상위 항목은 `parent_id`를 `null`로 적는다. 키를 생략하지 않고 값을 명시하여, 키를 빠뜨린 실수와 구분한다.
- 긴 설명은 `>-` 블록으로 적는다. 여러 줄로 적어도 한 줄의 문장으로 읽힌다.
- 파일 머리의 주석에 각 키의 의미를 적어, 사람이 파일만 열어도 항목을 알 수 있게 한다.
- 레코드를 적는 순서에는 제약이 없다([dp1.md](dp1.md)의 '원본에 적힌 순서와 외래 키 검사').

## 2. 변환

### 절차

변환 명령은 데이터 폴더를 입력받아 SQLite 파일 하나를 만든다. 변환 명령은 사용자가 실행한다. 조회 스크립트는 변환을 실행하지 않는다(DP-6).

원본이 작으므로(기능 100개 미만) 매번 데이터베이스 전체를 새로 만들며, 변경분만 반영하는 방식은 사용하지 않는다.

1. `features.yaml`을 읽는다.
2. 아래의 '검증 규칙'으로 원본을 검사한다. 오류가 하나라도 있으면 데이터베이스를 만들지 않고, 발견한 오류를 모두 출력한 뒤 종료한다. 기존 데이터베이스 파일은 그대로 둔다.
3. 임시 파일에 테이블과 뷰를 만들고, 외래 키 검사(`PRAGMA foreign_keys = ON`)를 켠 뒤 트랜잭션 하나로 레코드를 넣는다.
4. `build_info` 테이블에 생성 정보를 기록한다.
5. 임시 파일을 최종 경로로 옮긴다. 옮기기는 원자적으로 수행되므로, 조회 중에 반쯤 만들어진 데이터베이스를 읽는 일이 없다. 다른 프로그램이 데이터베이스 파일을 열고 있어 옮기지 못하면, 오류를 출력하고 기존 파일을 그대로 둔다.

### 검증 규칙

테이블의 제약(기본 키, 외래 키, `NOT NULL`)으로 잡을 수 있는 오류는 SQLite가 잡는다. 그러나 SQLite는 첫 번째 오류에서 멈추고 원본의 어느 레코드인지 알려 주지 않으므로, 변환 명령이 넣기 전에 먼저 검사하여 레코드 ID와 함께 모든 오류를 출력한다.

| 규칙 | 근거 |
|---|---|
| 여섯 개의 키가 모두 있다. 정의되지 않은 키가 없다. | 키의 오타와 누락을 잡는다. |
| 모든 값은 문자열이다. `parent_id`만 문자열 또는 `null`이다. | YAML은 따옴표가 없는 값을 다른 자료형으로 해석한다. 아래의 설명을 참고한다. |
| `parent_id`를 제외한 값은 비어 있지 않다. | `NOT NULL` |
| `id`가 중복되지 않는다. | 기본 키 |
| `parent_id`가 있으면 그 기능이 존재한다. | 외래 키 |
| 부모를 따라 올라갔을 때 순환하지 않는다. | 순환하면 계층 경로와 하위 트리가 정의되지 않는다. |
| `path`가 부모의 `path`에 ` > `와 자신의 `name`을 붙인 값과 같다. 최상위 항목은 `path`가 `name`과 같다. | 1장 |

YAML 해석기는 따옴표가 없는 값을 문자열이 아닌 자료형으로 바꾸는 경우가 있다. PyYAML로 확인한 결과, `id: NO`는 거짓(`False`)으로, `ims_ref: 0100`은 정수 64로, `name: 1.10`은 실수 1.1로 읽힌다. 이러한 값은 '비어 있지 않다'는 규칙을 통과하고 데이터베이스에는 원본과 다른 문자열로 저장되므로, 자료형을 검사하여 오류로 처리한다. 오류 메시지는 해당 값을 따옴표로 감싸도록 안내한다.

### 생성 정보

```sql
CREATE TABLE build_info (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
```

`build_info`는 데이터가 아닌 생성 정보를 담으며, 조회 스크립트의 최신성 검사([dp6.md](dp6.md))에 사용한다. 다음 세 개의 행을 기록한다.

| key | value |
|---|---|
| `source_hash` | 원본 파일 내용의 해시 |
| `schema_hash` | 테이블과 뷰를 정의하는 SQL 문의 해시 |
| `built_at` | 생성 시각 |

`schema_hash`를 두는 이유는 다음과 같다. 원본이 그대로여도 테이블이나 뷰의 정의를 고치면 데이터베이스를 다시 만들어야 한다. 원본의 해시만 비교하면 이 경우를 발견하지 못한다.

## 3. 데이터베이스의 위치

데이터베이스 파일은 데이터 폴더 아래의 `build/ftm.db`에 만든다. 데이터베이스는 원본에서 언제든 다시 만들 수 있는 파일이므로 git에 넣지 않는다. 데이터 폴더는 설정으로 전달받는 경로이므로(DP-6), `build/`는 데이터 폴더가 속한 저장소의 `.gitignore`에서 제외한다.

## 4. 논의

### 데이터베이스를 파일로 둘지, 질의마다 메모리에 만들지

| 설계안 | 얻는 것 | 잃는 것 |
|---|---|---|
| 파일로 두고 해시로 최신성 검사 (제안) | 시각화(FR-4)나 DB 도구가 같은 파일을 열 수 있다. 질의마다 원본을 해석하지 않는다. | 최신성 검사와 원자적 교체를 구현해야 한다. 원본을 고친 뒤 변환을 실행해야 한다. |
| 질의마다 원본을 읽어 메모리에 생성 | 최신성 문제가 원천적으로 없다. 파일을 쓰지 않는다. | 질의마다 원본 해석과 검증을 반복한다. 다른 도구와 데이터베이스를 공유할 수 없다. |

원본의 규모에서는 두 번째 안의 비용도 크지 않다. 그러나 전체 구조도(`docs/architecture.html`)가 'DB 생성'과 '조회용 SQLite DB'를 별도의 요소로 두고 있고, 시각화도 같은 데이터베이스를 사용할 수 있으므로 첫 번째 안을 제안한다.

## 5. 사용자의 결정이 필요한 사항

- 1장의 원본 형식과 2장의 검증 규칙을 채택할지 정한다.
- 3장의 데이터베이스 위치를 채택할지 정한다.
