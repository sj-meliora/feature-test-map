# DP-6 세부 설계: 조회 스크립트

> **상태: 결정됨**
> 이 문서는 `DESIGN.md`의 DP-6에서 결정한 내용을 구체화한다. 문서의 내용은 사용자가 채택하였으며 `DESIGN.md`의 DP-6에 반영하였다. 6장의 '미결'에 적은 항목은 제외한다.

## 범위

이 문서는 스킬(DP-6)의 구성과, 스킬에 포함되는 조회 스크립트의 명령, 최신성 검사, 읽기 전용의 보장, 결과 행의 제한을 다룬다. 테이블과 뷰의 정의는 [dp1.md](dp1.md)에, 변환과 생성 정보는 [dp4.md](dp4.md)에, 에이전트의 조회 절차는 [dp5.md](dp5.md)에 있다.

## 1. 스킬의 구성과 명령

### 변환 명령과 정의 파일의 위치

스킬은 다음 네 가지를 포함한다. 플러그인으로 설치하면 네 가지가 함께 설치된다.

| 구성 요소 | 내용 |
|---|---|
| 안내 문서 | 스키마 설명과 조회 절차([dp5.md](dp5.md)) |
| 조회 스크립트 | 읽기 전용으로 SQL을 실행한다. |
| 변환 명령 | 원본에서 데이터베이스를 만든다([dp4.md](dp4.md)). 사용자가 실행하며, 에이전트는 실행하지 않는다. |
| 정의 파일 | 테이블과 뷰를 정의하는 SQL 파일 하나([dp1.md](dp1.md)) |

변환 명령과 조회 스크립트는 Python으로 구현하며, 같은 정의 파일을 사용한다. 두 명령이 항상 함께 설치되므로, 같은 사본의 변환 명령이 데이터베이스에 기록하는 정의와 조회 스크립트가 참조하는 정의는 어긋나지 않는다.

스킬은 저장소 안과 플러그인이 설치된 경로의 두 곳에 있다. 조회 스크립트는 설치된 사본으로 동작하므로, 사용자는 **설치된 사본의 변환 명령**을 실행해야 한다. 설치 경로는 사용자가 직접 찾기 어려우므로, 조회 스크립트가 오류 메시지에 실행할 명령을 출력한다(2장).

저장소에서 정의 파일을 고친 뒤 플러그인을 다시 설치하지 않으면, 설치된 사본의 변환 명령과 조회 스크립트는 모두 이전 정의로 동작한다. 고친 내용이 아직 반영되지 않을 뿐이며 오류는 발생하지 않는다. 플러그인을 다시 설치하면 조회 스크립트가 정의의 변경을 발견하고 변환을 요구한다(2장).

### 조회 스크립트의 명령

조회 스크립트는 하위 명령 두 개를 제공한다.

| 명령 | 동작 |
|---|---|
| `schema` | 데이터 폴더의 절대 경로, 테이블과 뷰의 정의, 테이블별 레코드 수, 생성 시각을 출력한다. |
| `sql "<SELECT 문>"` | SQL 한 문장을 실행하고 결과를 표로 출력한다. |

기능 목록은 에이전트가 `features.yaml`을 직접 읽으므로(DP-5), 조회 스크립트에는 이를 출력하는 명령을 두지 않는다.

### 데이터 폴더의 경로

변환 명령과 조회 스크립트는 데이터 폴더의 경로를 환경 변수 `FTM_DATA_DIR`로 전달받는다. 데이터 폴더는 원본 파일(`features.yaml`)이 들어 있는 폴더이며, 데이터베이스도 이 폴더 아래에 만들어진다([dp4.md](dp4.md)).

- `FTM_DATA_DIR`이 설정되지 않았거나 그 경로에 폴더가 없으면, 두 명령은 환경 변수를 설정하라는 안내를 출력하고 오류로 종료한다. 기본 경로를 추측하여 사용하지 않는다. 예시 데이터를 실제 데이터로 착각하는 상황을 막기 위해서다.
- 에이전트는 환경 변수를 직접 해석하지 않고, 조회 스크립트의 출력에서 경로를 얻는다. 조회 스크립트는 `schema`의 출력과 최신성 검사의 오류 메시지(2장)에 데이터 폴더의 절대 경로를 포함한다.

## 2. 최신성 검사

### 오래된 데이터베이스의 처리

조회 스크립트는 명령을 실행하기 전에 데이터베이스의 최신성을 검사한다. 데이터베이스가 없거나 오래되었으면 **오류로 종료**하고, 변환 명령을 실행하라는 안내를 출력한다. 조회 스크립트는 데이터베이스를 다시 만들지 않으며, 오래된 데이터베이스로 질의를 실행하지도 않는다.

따라서 조회 스크립트는 어떤 파일도 쓰지 않는다. DP-6의 '읽기 전용'은 원본과 데이터베이스 모두에 대하여 문자 그대로 성립한다.

### 검사 방법

조회 스크립트는 다음 두 값을 `build_info` 테이블([dp4.md](dp4.md))에 기록된 값과 비교한다. 하나라도 다르면 데이터베이스가 오래된 것으로 판단한다.

| 비교하는 값 | 다를 때의 의미 |
|---|---|
| 원본 파일 내용의 해시 (`source_hash`) | 원본을 고친 뒤 변환하지 않았다. |
| 테이블과 뷰를 정의하는 SQL 파일 내용의 해시 (`schema_hash`) | 테이블이나 뷰의 정의를 고친 뒤 변환하지 않았다. |

조회 스크립트는 스킬 안의 정의 파일(1장)로 `schema_hash`를 계산한다. 같은 사본의 변환 명령도 같은 파일로 계산하므로, 그 변환 명령을 실행하면 두 값은 반드시 일치한다.

### 오류 메시지

조회 스크립트는 원인에 따라 서로 다른 메시지를 출력한다. 어느 경우에도 필요한 조치는 변환 명령의 실행이다.

| 상황 | 안내하는 내용 |
|---|---|
| 데이터베이스 파일이 없다. | 데이터베이스가 아직 만들어지지 않았다. 아래의 명령을 실행한다. |
| `source_hash`가 다르다. | 원본이 데이터베이스를 만든 뒤에 바뀌었다. 아래의 명령을 실행한다. |
| `schema_hash`가 다르다. | 데이터베이스가 이 스킬의 정의와 다른 정의로 만들어졌다. 아래의 명령을 실행한다. 저장소에서 정의를 고쳤다면 플러그인을 먼저 다시 설치한다. |

모든 메시지는 데이터 폴더의 절대 경로를 포함하며, **같은 사본에 포함된 변환 명령의 절대 경로와 데이터 폴더의 경로를 넣은 실행 줄**로 끝난다. 실행 줄은 `FTM_DATA_DIR`의 값을 함께 지정하므로, 사용자의 셸에 환경 변수가 설정되어 있지 않아도 그대로 실행할 수 있다. 조회 스크립트는 자신이 설치된 위치를 알 수 있으므로, 같은 사본의 변환 명령의 경로를 구할 수 있다. 사용자가 메시지에 적힌 줄을 그대로 실행하면 변환 명령과 조회 스크립트가 같은 사본의 정의를 사용하므로, 오류가 반드시 해소된다.

실행 줄을 출력하지 않으면 다음 경우에 오류가 해소되지 않는다. 사용자가 저장소에서 정의 파일을 고치고 저장소의 변환 명령을 실행하면, 데이터베이스는 새 정의로 만들어지지만 설치된 조회 스크립트는 이전 정의를 참조한다. 조회 스크립트는 변환을 요구하고, 사용자가 저장소의 변환 명령을 다시 실행해도 결과는 같다.

이 경우에 메시지의 실행 줄을 따르면 오류는 해소되지만, 데이터베이스는 설치된 사본의 이전 정의로 만들어진다. 저장소에서 고친 정의를 반영하려면 플러그인을 다시 설치한 뒤 변환해야 하므로, `schema_hash`가 다른 경우의 메시지에 이 안내를 함께 넣는다.

### 에이전트의 변환 실행

에이전트는 변환 명령을 실행하지 않는다. 조회 스크립트가 오류로 종료하면, 에이전트는 오류 메시지의 내용과 실행 줄을 사용자에게 그대로 전달한다([dp5.md](dp5.md)). 데이터베이스는 사용자가 변환 명령을 실행할 때에만 만들어진다.

## 3. 읽기 전용의 보장

스킬에는 데이터베이스 파일을 쓰는 변환 명령이 포함되지만, 조회 스크립트는 변환 명령을 호출하지 않으며 어떤 파일도 쓰지 않는다. 변환 명령은 데이터 폴더의 `build/` 아래에만 쓰고 원본은 바꾸지 않는다.

조회 스크립트는 다음 세 겹으로 쓰기를 막는다.

1. 데이터베이스를 읽기 전용 모드로 연다(`file:...?mode=ro`).
2. `PRAGMA query_only = ON`을 설정한다.
3. SQLite의 권한 확인 콜백(authorizer)에서 읽기, 선택, 함수 호출, 재귀 질의만 허용한다. `ATTACH`, `PRAGMA`, 쓰기 문은 실행 전에 거부된다.

시험용 스크립트에서 `DELETE`, `ATTACH`, `PRAGMA writable_schema = 1`이 모두 `not authorized`로 거부됨을 확인하였다.

## 4. 결과 행의 제한

결과가 지나치게 길면 에이전트의 컨텍스트를 차지하므로, 출력하는 행의 수를 제한하고, 제한을 넘으면 잘렸다는 표시를 출력한다. 제한 값은 미결이며(6장), 구현에는 200행을 기본값으로 둔다. 기능은 100개 미만이므로 기능 테이블만 있는 지금은 제한에 걸리지 않으나, TC가 추가되면 필요해진다.

잘린 결과를 에이전트가 세면 개수가 틀리므로, 안내 문서에 '개수는 반드시 `COUNT`로 구한다'는 규칙을 둔다([dp5.md](dp5.md)의 조회 절차).

행의 제한은 출력의 분량만 줄이며, 질의의 실행 시간은 제한하지 않는다. 3장의 권한 확인 콜백은 재귀 질의를 허용하므로, 종료하지 않는 재귀 질의나 큰 교차 조인을 막지 못한다. 기능 테이블만 있는 지금은 문제가 되지 않으며, TC가 추가될 때 실행 시간의 제한을 검토한다.

## 5. 논의

### 오래된 데이터베이스를 발견했을 때

| 설계안 | 얻는 것 | 잃는 것 |
|---|---|---|
| 조회 스크립트가 다시 변환한 뒤 질의 | 사용자가 변환을 신경 쓰지 않아도 된다. | 조회 스크립트가 데이터베이스 파일을 쓰므로, DP-6의 '읽기 전용'을 '원본을 바꾸지 않는다'로 다시 해석해야 한다. 데이터베이스가 만들어지는 시점이 둘로 나뉜다. |
| 경고만 출력하고 기존 데이터베이스로 질의 | 조회 스크립트가 아무 파일도 쓰지 않는다. | 에이전트가 경고를 무시하면 이전 데이터로 답한다. |
| 오류로 종료하고 변환을 요구 (채택) | 조회 스크립트가 아무 파일도 쓰지 않는다. 이전 데이터로 답하는 일이 없다. 데이터베이스가 만들어지는 시점이 '사용자가 변환 명령을 실행할 때' 하나로 정해진다. | 원본을 고친 뒤 변환 명령을 실행하는 단계가 생긴다. |

세 번째 안을 채택하였다. 사용자가 한 명이며 원본을 고치는 사람과 질의하는 사람이 같으므로, 변환 단계가 하나 늘어나는 부담은 크지 않다. DP-6의 문구를 고칠 필요가 없고, 다른 프로그램이 데이터베이스 파일을 열고 있는 동안 조회 스크립트가 파일을 교체하려다 실패하는 경우도 생기지 않는다.

### 정의 파일과 변환 명령을 어디에 둘지

조회 스크립트는 플러그인으로 설치된 사본으로 동작한다. 변환 명령과 정의 파일을 스킬 밖의 저장소에 두면, 정의를 고치고 변환을 실행했으나 플러그인을 다시 설치하지 않은 경우에 조회 스크립트가 참조하는 정의와 데이터베이스의 `schema_hash`가 계속 어긋난다. 이때 조회 스크립트는 변환을 요구하지만, 변환을 실행해도 오류가 해소되지 않는다.

| 설계안 | 얻는 것 | 잃는 것 |
|---|---|---|
| 정의 파일과 변환 명령을 스킬 안에 함께 둠 (채택) | 오류 메시지의 실행 줄을 따르면 변환과 조회가 같은 사본을 사용하므로, 해소되지 않는 오류가 생기지 않는다. `schema_hash`가 다른 원인이 '변환을 실행하지 않음' 하나로 줄어든다. | 스킬에 파일을 쓰는 명령이 포함된다. |
| 저장소에 두고, 해시 대신 스키마의 버전 번호를 비교 | 스킬은 읽기 전용 스크립트만 포함한다. 번호의 크기를 비교하여 '변환을 실행하지 않음'과 '플러그인을 갱신하지 않음'을 구분할 수 있다. | 정의를 고칠 때마다 번호를 직접 올려야 하며, 잊으면 검사가 동작하지 않는다. |

사람이 기억해야 할 절차가 늘지 않고 오류의 원인이 하나로 정리되므로 첫 번째 안을 채택하였다. 조회 스크립트는 변환 명령과 별개의 명령이고 그대로 읽기 전용이므로, DP-6의 '읽기 전용 조회 스크립트'는 유지된다.

### 에이전트가 변환 명령을 실행하도록 허용할지

변환 명령이 스킬 안에 있으므로, 에이전트가 실행할 수 있는 위치에 있다.

| 설계안 | 얻는 것 | 잃는 것 |
|---|---|---|
| 허용하지 않음 (채택) | 데이터베이스가 만들어지는 시점이 '사용자가 변환 명령을 실행할 때' 하나로 유지된다. 에이전트는 어떤 파일도 쓰지 않는다. | 원본을 고친 뒤 사용자가 명령을 직접 실행해야 한다. |
| 허용함 | 사용자가 변환을 신경 쓰지 않아도 된다. | 채택하지 않은 '조회 스크립트가 다시 변환' 안과 결과가 같아진다. 데이터베이스가 만들어지는 시점이 둘로 나뉜다. |

데이터베이스가 만들어지는 시점을 하나로 정하는 것이 '오류로 종료' 안을 채택한 근거였으므로, 허용하지 않는 안을 채택하였다. 오류 메시지에 실행 줄이 출력되므로, 사용자는 그 줄을 그대로 실행하면 된다.

### 데이터 폴더의 경로를 전달하는 수단

| 설계안 | 얻는 것 | 잃는 것 |
|---|---|---|
| 환경 변수 (채택) | 구현이 가장 단순하다. 실행 주체를 MCP 서버로 옮겨도 서버 설정의 환경 변수로 그대로 전달할 수 있다. | 에이전트를 실행하기 전에 값을 설정해 두어야 한다. |
| 명령줄 인자 | 실행 줄만 보아도 대상 데이터가 드러난다. | 에이전트가 호출할 때마다 경로를 넣어야 하며, 에이전트가 그 경로를 알아내는 방법이 따로 필요하다. |
| 설정 파일 | 여러 설정을 함께 관리할 수 있다. | 설정 파일의 위치 규칙과 읽는 코드가 추가된다. 전달할 값은 경로 하나뿐이다. |

전달할 값이 하나뿐이므로 환경 변수를 채택하였다.

## 6. 미결

- 결과 행의 제한 값을 정해야 한다. 구현에는 200행을 기본값으로 두며, TC 레코드가 추가될 때 값을 확정한다.
