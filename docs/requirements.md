# Feature-Test Map 요구사항

상태: 초안. 각 항목 끝에 붙은 표시는 그 항목의 출처를 나타낸다.

- **[합의]** 논의에서 결정한 것
- **[제안]** 아직 확정하지 않은 제안
- **[미정]** 결정이 필요한 것 (9장에 모음)

## 1. 배경

SSD FW를 FPGA 위에서 동작시키는 TC set의 테스트 커버리지를 평가할 기준이 필요하다. 코드 라인·브랜치 커버리지를 측정하는 도구는 이 환경에서 사용하기 어렵다. 따라서 "검증해야 할 기능 공간을 TC set이 얼마나 덮는가"를 평가 기준으로 삼는다.

## 2. 목적

- 기존 TC set이 기능 공간을 덮는 정도를 숫자와 지도로 보여준다. [합의]
- 어떤 기능과 조건이 검증되지 않았는지 찾을 수 있게 한다. [합의]
- 숫자의 근거를 TC 단위까지 추적할 수 있게 한다. [합의]

## 3. 범위

### 포함

- **의도 커버리지:** TC의 이름, 코드, 문서만 보고 판단하는 커버리지. [합의]
- 폭(기능 목록 대비)과 깊이(기능별 시나리오 공간 대비) 두 수준. [합의]

### 제외

- **달성 커버리지:** 실행 중 FW 내부 관측(카운터, 로그)으로 확인하는 커버리지. 나중에 붙일 수 있게 구조만 열어둔다. [합의]
- 코드 구조 커버리지(라인, 브랜치, 함수). [합의]
- 성능·복구 시간 같은 정량 기준. Response measure는 "무엇을 확인하는가"까지만 본다. [제안]

## 4. 용어

| 용어 | 뜻 |
|---|---|
| 기능 | IMS structure 메뉴에 나열된 항목 하나 |
| 시나리오 템플릿 | 기능 하나에 대해 Stimulus, Environment, Response, Response measure별로 가능한 값을 열거한 표 (general scenario) |
| 인스턴스 | 템플릿의 값 하나 (예: SES = User Data Erase) |
| cross | 함께 교차해서 볼 축의 조합을 선언한 것 |
| 조합 | cross를 풀어 나온 인스턴스 묶음 하나 (concrete scenario) |
| TC 역할 | 검증 목적 / 사전 준비 / 부수적 |
| 확실성 | 반드시(TC 코드상 반드시 발생) / 가능(랜덤이라 발생할 수 있음) |
| 제외 | 제품 미지원 등으로 검증 대상이 아닌 것 |
| 도달 불가 | 검증해야 하지만 TC가 그 상태를 만들 수단이 없는 것 |

## 5. 입력

| 입력 | 용도 | 비고 |
|---|---|---|
| IMS structure 기능 목록 | 분모의 최상위 축 | 최상위 목록 수준이고 하위 계층은 드물다. 식별 외의 정보는 기대하지 않는다. [합의] |
| TC set | 분자 | 규모와 형태 [미정] |
| NVMe 스펙 | 호스트에서 보이는 기능의 인스턴스 출처 | 제품이 따르는 리비전 [미정] |
| 설계 문서, 담당자 | 내부 기능의 인스턴스 출처 | 접근 가능 범위 [미정] |

## 6. 기능 요구사항

### 6.1 단계 1: 기능 목록

- **FR-01** IMS structure에서 기능 목록을 뽑아 분모로 삼는다. [합의]
- **FR-02** 기능마다 고유 ID와 IMS 식별자를 기록한다. [제안]
- **FR-03** 평가 대상에서 빼는 기능은 삭제하지 않고 제외로 표시하고 사유를 적는다. [제안]

### 6.2 단계 2: 폭

- **FR-10** TC마다 어떤 기능을 건드리는지 매핑한다. [합의]
- **FR-11** 매핑마다 역할(검증 목적 / 사전 준비 / 부수적)과 판정 근거를 기록한다. [제안]
- **FR-12** 검증 목적 TC가 하나 이상 있는 기능을 폭에서 덮인 것으로 본다. [제안]
- **FR-13** 검증 대상이 기능 목록에 없는 TC를 따로 모은다. 기능 목록의 누락을 찾는 용도다. [제안]
- **FR-14** TC별 원시 사실(사용 커맨드와 파라미터, 사전 절차, 확인 항목)을 기록해 단계 4에서 다시 쓴다. [제안]

### 6.3 단계 3: 시나리오 공간

- **FR-20** 기능마다 시나리오 템플릿을 만든다. 요소는 Stimulus, Environment, Response, Response measure다. [합의]
- **FR-21** 인스턴스는 스펙과 설계 문서에서 뽑는다. 기존 TC에서 뽑지 않는다. [제안]
- **FR-22** 인스턴스마다 출처를 적는다. [제안]
- **FR-23** 제외와 도달 불가는 사유와 함께 표시하고 분모에서 뺀다. [제안]
- **FR-24** cross는 축 조합 단위로 선언하고, 그 안의 조합은 전부 기계적으로 나열한다. 개별 시나리오를 골라 담지 않는다. [제안]
- **FR-25** 성립하지 않는 조합은 사유와 함께 제외한다. [제안]
- **FR-26** 전 기능을 한 번에 하지 않고 우선순위가 높은 기능부터 한다. 우선순위 기준 [미정]

### 6.4 단계 4: 깊이

- **FR-30** TC가 덮는 인스턴스를 실행(run) 단위로 매핑한다. 한 TC가 여러 run을 가질 수 있다. [제안]
- **FR-31** run마다 확실성(반드시 / 가능)을 기록한다. [제안]
- **FR-32** 인스턴스 커버리지 = 반드시 덮인 유효 인스턴스 수 ÷ 유효 인스턴스 수. [합의]
- **FR-33** 조합 커버리지 = 덮인 유효 조합 수 ÷ 유효 조합 수. 한 run 안에 조합의 인스턴스가 모두 있어야 덮인 것으로 본다. [제안]
- **FR-34** "가능"은 분자에 넣지 않고 따로 센다. [제안]

### 6.5 보고와 시각화

- **FR-40** 전체 요약: 기능별 폭, 인스턴스 커버리지, 조합 커버리지를 분모와 함께 보여준다. [합의]
- **FR-41** 시나리오를 만들지 않은 기능은 0%가 아니라 미분석으로 표시한다. [합의]
- **FR-42** 기능별 상세: 시나리오 표의 인스턴스를 상태별로 구분해 보여준다. [합의]
- **FR-43** cross별 격자를 보여준다. [합의]
- **FR-44** 인스턴스에서 TC로, TC에서 인스턴스로 양방향 추적이 된다. [합의]
- **FR-45** 기능별 퍼센트를 단순 합산한 전체 숫자는 만들지 않는다. [제안]

## 7. 비기능 요구사항

- **NFR-01 재현성:** 같은 입력이면 같은 숫자가 나온다. IMS 추출 시점, TC set 리비전, 스펙 리비전을 기록한다. [합의]
- **NFR-02 판정 일관성:** 매핑 판정 규칙을 글로 적어 평가자가 달라도 결과가 같게 한다. [합의]
- **NFR-03 분리:** 정의(분모), 매핑(분자), 계산 결과를 따로 저장한다. 숫자는 손으로 적지 않고 계산한다. [합의]
- **NFR-04 변경 이력:** 정의와 매핑의 변경이 리뷰 가능한 단위로 남는다. [제안]
- **NFR-05 확장성:** 달성 커버리지, 정량 기준, FW 버전별 추이를 기존 구조를 바꾸지 않고 추가할 수 있다. [합의]
- **NFR-06 검증:** 없는 ID 참조, 사유 없는 제외 같은 오류를 계산 전에 잡는다. [제안]

## 8. 알려진 한계

- 의도 커버리지는 TC가 의도한 것을 센다. 실행 중 그 상태가 실제로 만들어졌는지는 보장하지 않는다.
- 내부 상태 축(GC 중, 블록 고갈 직전 등)은 TC가 그 상태를 만드는 절차를 갖고 있는지로만 판단할 수 있다.
- 랜덤·스트레스 TC는 "가능"으로만 기록된다.
- 목록에 없는 기능과 인스턴스는 보이지 않는다. FR-13과 유출 결함 대조로 보완한다.

## 9. 미정 사항

| # | 질문 | 영향받는 항목 |
|---|---|---|
| Q1 | 이 기준의 용도가 릴리스 게이트인가, 공백 찾기인가? | 숫자의 엄격함, FR-45, 목표치 설정 여부 |
| Q2 | 결과를 보는 사람은 누구인가? | 시각화 수준, 용어 |
| Q3 | TC set의 규모와 형태(언어, 프레임워크)는? | FR-14 자동화 여부, 일정 |
| Q4 | IMS 목록은 어떻게 내보내고 얼마나 자주 바뀌는가? | FR-01, NFR-01 |
| Q5 | IMS 목록에 없는 내부 기능(GC, 복구 등)이 드러나면 분모에 추가하는가, 별도로 보고만 하는가? | FR-13, 분모의 정의 |
| Q6 | 깊이 분석할 기능의 우선순위 기준은? | FR-26 |
| Q7 | 시나리오 템플릿은 누가 리뷰하고 승인하는가? | FR-20~25, NFR-04 |
| Q8 | 제품이 따르는 NVMe 리비전과 미지원 기능 목록은 어디서 확인하는가? | FR-21, FR-23 |
| Q9 | 저장소와 산출물을 어디에 두는가? (사내 정보 포함) | NFR-04, 공유 방식 |

## 10. 단계

1. IMS structure에서 기능 목록 추출
2. TC set을 분석해 폭 산출
3. 기능별 시나리오 구성 (우선순위 기능부터, 두세 개로 먼저 시험)
4. TC set을 다시 분석해 깊이 산출
