# FR-1 탐색 안내: IMS structure에서 기능 목록을 얻기 위한 사전 조사

> **이 문서를 읽는 대상**: IMS structure에 접근할 수 있는 사내 에이전트다. 이 문서를 끝까지 읽은 뒤에 IMS structure의 탐색을 시작한다.
>
> **이 문서의 성격**: 작업 안내다. 설계 결정을 기록하는 문서가 아니다. '결정된 내용'으로 표시한 부분은 `DESIGN.md`에서 옮긴 것이며, 서로 다르면 `DESIGN.md`가 기준이다. 그 밖의 부분(탐색할 질문, 작업 순서, 보고 형식)은 이 문서에서 처음 제시하는 것이다.

## 1. 이번 작업의 범위

이 프로젝트는 SSD FW의 기능을 인스턴스 시나리오로 세분하고, 시나리오와 TC 사이의 관계를 저장하여, 검증되지 않은 공백을 찾는다. 그 출발점이 FR-1이다.

> **FR-1**: IMS structure에서 검증해야 할 기능 목록을 추출하여 저장한다.

기능 목록을 저장하는 형식은 정해져 있으나(3장), IMS structure에서 그 형식의 데이터를 **어떻게 얻을지는 정해지지 않았다**. 이 프로젝트의 설계는 IMS structure를 직접 보지 않은 상태에서 이루어졌기 때문이다. 방법을 정하려면 IMS structure가 실제로 어떤 모습인지를 먼저 알아야 한다.

따라서 이번 작업은 **추출이 아니라 탐색**이다.

| 이번 작업에서 하는 것 | 이번 작업에서 하지 않는 것 |
|---|---|
| IMS structure의 형태와 접근 수단을 파악한다. | 기능 목록 전체를 추출하지 않는다. |
| 4장의 질문에 사실로 답한다. | 정해지지 않은 사항을 스스로 결정하지 않는다. |
| 대표 항목 몇 개를 정해진 형식으로 시범 변환한다. | 인스턴스 시나리오, TC, 관계를 다루지 않는다. |
| 결과를 보고서로 정리한다(7장). | `DESIGN.md`와 그 밖의 설계 문서를 고치지 않는다. |

## 2. 기능 레코드가 쓰이는 곳

탐색에서 무엇을 눈여겨보아야 하는지는 기능 레코드의 쓰임에서 나온다.

- **인스턴스 시나리오가 기능에 속한다.** 검증 대상인 기능마다 인스턴스 시나리오를 하나 이상 두며, 시나리오는 자극, 환경, 응답, 응답 측정의 네 단계로 기능을 구체화한다. 기능의 설명이 부실하면 시나리오를 작성할 근거가 없다.
- **TC는 시나리오를 거쳐 기능에 연결된다.** TC가 어느 기능을 검증하는지를 식별할 때(FR-3) 기능의 설명을 근거로 사용한다.
- **LLM이 기능 목록 전체를 읽고 질의에 답한다.** '전원과 관련된 기능은 무엇인가'와 같이 의미로 찾는 질의는 기능의 이름과 설명만으로 판단한다(FR-5).
- **기능의 ID가 모든 연결의 기준이다.** 시나리오의 ID는 `<기능 ID>-S<번호>` 형식이며, 관계와 보고서가 모두 기능 ID를 거친다. ID가 바뀌면 연결이 모두 끊어진다.

요약하면, 기능 레코드에서 가장 중요한 항목은 **안정적인 ID**와 **내용이 충분한 설명**이다. IMS structure가 이 두 가지를 얼마나 제공하는지가 탐색의 핵심이다.

## 3. 결정된 내용: 기능 레코드의 형식

이 장의 내용은 `DESIGN.md`의 DP-1과 DP-4, `design/dp1.md`, `design/dp4.md`에서 옮긴 것이다.

### 설계의 전제

설계는 IMS structure에 대하여 다음을 전제하였다. 이 전제는 확인된 사실이 아니며, **맞는지 확인하는 것이 탐색의 목적 가운데 하나다**.

- 기능의 개수는 100개 미만이다.
- IMS structure는 최상위 목록 위주로 구성되며, 하위 목록이 있는 경우는 드물다.
- 한 세대 안에서는 IMS structure가 변하지 않는다.

### 항목

기능 하나를 레코드 하나로 저장한다. 원본 파일은 데이터 폴더의 `features.yaml`이다.

| 키 | 의미 | 규칙 |
|---|---|---|
| `id` | 고유 ID | **사용자가 직접 부여한다.** 한 세대 안에서 바뀌지 않는다. |
| `name` | 이름 | 사람이 기능을 식별하는 이름이다. |
| `path` | 계층 경로 | 최상위 항목부터 자신까지의 `name`을 ` > `로 이은 문자열이다. |
| `parent_id` | 부모 기능의 `id` | 최상위 항목은 `null`로 명시한다. 키를 생략하지 않는다. |
| `description` | 자연어 설명 | 의미로 찾는 질의와 관계 식별에 사용한다. 아래 '설명의 근거'에 따라 작성한다. |
| `ims_ref` | IMS 원본 위치 | IMS 항목의 key를 적는다. URL은 적지 않는다. 추출한 결과를 IMS structure의 원본과 대조하고 설명의 근거를 찾아가는 데 사용한다. |

### 설명의 근거

IMS 항목의 대부분은 epic이며, 본문만으로는 설명을 채우기 어렵다. `description`은 `ims_ref`가 가리키는 항목에서 도달할 수 있는 다음 자료만을 근거로 작성한다.

| 순위 | 근거 자료 | 사용하는 경우 |
|---|---|---|
| 1 | 항목의 본문 | 항상 사용한다. |
| 2 | 항목에 속한 task의 제목과 본문 | 항상 사용한다. |
| 3 | 항목에 달린 comment | 1순위와 2순위의 자료로 기능의 동작과 조건을 알 수 없는 경우에만 사용한다. |

- 기능이 무엇을 하는지와 어떤 조건에서 어떻게 동작하는지를 적는다. 근거 자료에 있더라도 작업 내용(리팩터링, 로그 추가 등), 일정, 버그 이력, 채택되지 않은 제안은 적지 않는다.
- comment에는 채택되지 않은 제안과 지난 논의가 섞여 있다. comment의 내용을 사용할 때에는 현재의 동작을 말하는 내용인지 확인한다.
- 다른 IMS 항목이나 IMS 밖의 자료에 있는 내용은 넣지 않는다. 근거를 기록하는 키를 따로 두지 않으므로, 근거는 `ims_ref`에서 찾아갈 수 있는 범위에 있어야 한다.

### 구조의 규칙

- 트리로 중첩하지 않고 평면 목록으로 적는다. 계층은 `parent_id`와 `path`로 나타낸다.
- **자식 항목이 없는 말단 항목이 검증 대상이다.** 자식 항목을 가지는 상위 항목은 묶음이며, 검증 대상이 아니다. 검증 대상인지를 나타내는 키는 따로 없다.
- **task는 기능 레코드로 옮기지 않는다.** task는 작업 단위이며 기능이 아니다. 여기서 말하는 자식 항목에도 포함하지 않으므로, task를 가지는 epic도 하위 기능이 없으면 검증 대상이다.
- 레코드를 적는 순서에는 제약이 없다.

### 검증 규칙

변환 명령은 다음 규칙으로 원본을 검사하며, 하나라도 어긋나면 데이터베이스를 만들지 않는다.

- 여섯 개의 키가 모두 있고, 그 밖의 키가 없다.
- 모든 값은 비어 있지 않은 문자열이다. `parent_id`만 문자열 또는 `null`이다.
- `id`가 중복되지 않는다.
- `parent_id`가 있으면 그 기능이 존재하고, 부모를 따라 올라갔을 때 순환하지 않는다.
- `path`가 부모의 `path`에 ` > `와 자신의 `name`을 붙인 값과 같다. 최상위 항목은 `path`가 `name`과 같다.

YAML은 따옴표가 없는 값을 다른 자료형으로 해석한다. 예를 들어 `NO`는 거짓으로, `0100`은 정수 64로, `1.10`은 실수 1.1로 읽힌다. 이러한 값은 따옴표로 감싼다. IMS structure의 식별자가 숫자로만 이루어져 있다면 특히 주의한다.

### 예시

아래는 **예시 데이터**다. 실제 IMS structure에서 추출한 내용이 아니다. 전체 예시는 `examples/features.yaml`에 있다.

```yaml
- id: NS
  name: Namespace Management
  path: Namespace Management
  parent_id: null
  description: >-
    호스트가 namespace를 생성하고 삭제하는 기능의 묶음이다.
  ims_ref: IMS-EX-0100

- id: NS-CREATE
  name: Namespace Create
  path: Namespace Management > Namespace Create
  parent_id: NS
  description: >-
    Namespace Management 커맨드(Create)로 미할당 용량에서 새 namespace를
    만들고 NSID를 할당한다. 용량이 부족하거나 namespace 수가 최대에
    도달하면 오류로 완료한다.
  ims_ref: IMS-EX-0101
```

`NS`는 자식 항목을 가지므로 묶음이고, `NS-CREATE`가 검증 대상이다.

## 4. 탐색으로 답해야 하는 질문

아래의 질문은 모두 정해지지 않은 사항이다. 각 질문에 **확인한 사실**로 답하며, 어떻게 확인하였는지를 함께 적는다. 확인하지 못한 질문은 확인하지 못하였다고 적는다.

### A. 형태와 접근 수단

1. IMS structure는 어디에 있는가. 어떤 도구나 시스템이 관리하는가.
2. 읽을 수 있는 수단은 무엇인가. API, 명령줄 도구, 내보내기 파일, 화면 가운데 어느 것이 있는가.
3. 내보낼 수 있다면 형식은 무엇인가(예: 표 형식의 파일, 구조화된 문서).
4. 읽는 데 필요한 권한이나 절차가 있는가.

이 질문의 답이 추출을 자동화할 수 있는지를 결정한다.

### B. 규모와 계층

1. 항목은 모두 몇 개인가. '기능 100개 미만'이라는 전제에 맞는가.
2. 계층의 깊이는 얼마인가. 하위 목록을 가지는 항목은 몇 개인가. '최상위 목록 위주'라는 전제에 맞는가.
3. 계층의 각 단계는 무엇을 뜻하는가(예: 영역, 기능, 세부 기능). 단계마다 성격이 다른가.

### C. 항목이 가지는 정보

1. 항목 하나에 어떤 속성이 있는가. 속성의 이름과 뜻을 모두 나열한다.
2. 항목을 가리키는 **고유 식별자**가 있는가. 그 식별자는 항목의 이름이나 위치가 바뀌어도 유지되는가.
3. 항목에 **설명**이 있는가. 있다면 길이와 내용은 어느 정도인가. '무엇을 하는 기능인지'와 '어떤 조건에서 어떻게 동작하는지'를 알 수 있는가.
4. 설명이 없거나 부족하다면, 항목에서 연결된 다른 자료(규격 문서, 요구사항 문서 등)가 있는가.

C-2의 답이 `ims_ref`에 적을 값과 `id`를 부여하는 방법의 근거가 되고, C-3과 C-4의 답이 `description`을 채울 수 있는지를 결정한다.

### D. 검증해야 할 기능의 선별

1. IMS structure의 모든 항목이 검증해야 할 기능인가. 기능이 아닌 항목(예: 문서 항목, 관리용 항목, 폐기된 항목)이 섞여 있는가.
2. 섞여 있다면, 구분할 수 있는 속성(유형, 상태 등)이 있는가. 없다면 무엇을 보고 구분할 수 있는가.

### E. 이름

1. 이름이 같은 항목이 있는가. 특히 **같은 부모 아래에 이름이 같은 형제 항목**이 있는가. 있으면 `path`가 중복되며, 이 경우의 처리는 DP-1의 미결 사항이다.
2. 이름에 ` > `(공백, 부등호, 공백)가 들어 있는 항목이 있는가. `path`의 구분 문자열과 겹친다.
3. 이름은 어떤 언어와 표기로 적혀 있는가. 약어만으로 이루어진 이름이 많은가.

### F. 세대와 변경

1. 세대는 IMS structure에서 어떻게 구분되는가. 세대마다 별도의 structure가 있는가, 하나의 structure에 세대가 표시되는가.
2. '한 세대 안에서는 변하지 않는다'는 전제에 맞는가. 변경 이력을 볼 수 있다면 실제 변경 빈도는 어떠한가.
3. 세대가 바뀔 때 같은 기능을 가리키는 항목을 서로 대응시킬 수 있는 식별자가 있는가.

### G. 전제와 어긋나는 점

3장의 전제와 형식 가운데 IMS structure의 실제 모습과 맞지 않는 것이 있으면 모두 적는다. 질문에 없더라도, 여섯 개의 항목으로 담기 어려운 정보나 구조를 발견하면 적는다.

## 5. 작업 순서

1. **접근 수단을 확인한다.** A의 질문에 먼저 답한다. 읽을 수 없으면 여기서 멈추고, 무엇이 막혔는지를 사용자에게 알린다.
2. **전체를 훑어 수치를 구한다.** 항목의 수, 계층의 깊이, 하위 목록을 가지는 항목의 수, 설명이 있는 항목의 수를 센다. 세는 일은 눈으로 하지 않고 도구로 한다.
3. **질문에 답한다.** 4장의 순서대로 답하며, 답마다 확인한 방법을 적는다.
4. **대표 항목을 시범 변환한다.** 서로 다른 경우를 대표하는 항목 5개에서 10개를 골라 3장의 형식으로 옮긴다. 다음 경우를 가능한 한 포함한다.
   - 하위 항목이 없는 최상위 항목
   - 하위 항목을 가지는 항목과 그 하위 항목
   - 설명이 충분한 항목과 설명이 없거나 부족한 항목
   - 3장의 형식으로 옮기기 어려웠던 항목
5. **시범 변환한 결과를 검사한다.** 아래 '시범 변환의 검사'의 방법으로 검증 규칙에 맞는지 확인한다.
6. **보고서를 작성한다.** 7장의 형식을 따른다.

### 시범 변환의 검사

변환 명령은 네 원본 파일이 모두 있어야 데이터베이스를 만들므로, 기능 원본만 있는 상태에서는 변환할 수 없다. 기능 원본만 검사하려면 저장소 최상위에서 변환 명령에 `--check-features`를 주어 실행한다. `<파일 경로>`에는 시범 변환한 파일의 경로를 넣는다. `python3`이 없는 환경(Windows 등)에서는 `python`으로 실행한다.

```bash
python3 .claude/skills/ftm-query/scripts/build.py --check-features "<파일 경로>"
```

이 명령은 3장의 검증 규칙으로 그 파일만 검사하며, 데이터베이스를 만들지 않고 환경 변수의 지정도 필요하지 않다. `examples/features.yaml`에 실행하면 '기능 레코드: 8개 (묶음 1개, 검증 대상 7개)'가 출력된다.

## 6. 지켜야 할 것

- **IMS structure는 읽기만 한다.** 항목을 만들거나 고치거나 지우지 않는다.
- **사실과 추정을 구분한다.** 직접 확인한 것, 일부만 보고 추정한 것, 확인하지 못한 것을 섞어 적지 않는다. 일부 항목만 보고 전체에 대하여 말할 때에는 몇 개를 보았는지 적는다.
- **기능의 ID를 확정하지 않는다.** ID는 사용자가 직접 부여한다. 시범 변환에서는 ID의 후보를 적고 후보임을 표시하며, 그 후보를 어떤 규칙으로 만들었는지를 보고한다.
- **설명을 지어내지 않는다.** 3장의 '설명의 근거'에 정한 자료(항목의 본문, 항목에 속한 task, 항목에 달린 comment)에 없는 내용을 `description`에 넣지 않는다. 원문을 다듬거나 요약한 경우에는 원문과 함께 보인다. 설명을 채울 근거가 없는 항목은 비워 두고 그 사실을 보고한다.
- **정해지지 않은 사항을 스스로 결정하지 않는다.** 추출 방법, 검증 대상의 선별 기준, 중복된 `path`의 처리와 같은 사항은 선택지와 근거를 보고하고, 결정은 사용자에게 맡긴다.
- **설계 문서를 고치지 않는다.** 결정된 내용이 IMS structure의 실제 모습과 맞지 않으면 고치지 않고 보고한다.
- **실제 데이터를 예시 데이터와 섞지 않는다.** 시범 변환한 파일과 보고서를 `examples/`에 넣지 않는다. 저장할 위치와 저장소에 넣을지는 사용자에게 확인한다.

## 7. 보고서의 형식

탐색을 마치면 다음 구성으로 보고한다.

| 절 | 내용 |
|---|---|
| 요약 | IMS structure의 형태, 규모, 그리고 3장의 형식으로 옮기는 데 가장 큰 걸림돌을 서너 문장으로 적는다. |
| 접근 수단 | 무엇으로 어떻게 읽었는지, 자동화할 수 있는 수단이 있는지를 적는다. |
| 질문별 답 | 4장의 A부터 F까지의 질문마다 답, 확인한 방법, 확신의 정도(확인함, 추정함, 확인하지 못함)를 적는다. |
| 전제와 어긋나는 점 | 3장의 전제와 형식 가운데 실제와 맞지 않는 것을 적는다. 없으면 없다고 적는다. |
| 시범 변환 | 변환한 레코드, 항목마다 값을 어디에서 얻었는지, 변환하면서 내린 판단, 검사의 결과를 적는다. |
| 추출 방법의 선택지 | 탐색한 결과에 비추어 가능한 추출 방법을 나열하고, 방법마다 얻는 것과 잃는 것을 적는다. 하나를 추천할 수 있으면 근거와 함께 추천한다. |
| 사용자에게 확인할 것 | 탐색만으로는 답할 수 없어 사용자의 판단이 필요한 사항을 적는다. |
